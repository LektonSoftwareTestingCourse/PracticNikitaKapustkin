# Test-design ядра: Authorization и Card-Management

## 0. Требования и соглашения

### Требования ядра

В ТЗ нет нумерации требований, поэтому идентификаторы присвоены при анализе; в скобках - раздел ТЗ.

| ID | Требование |

| AUTH-02 | Статус `INACTIVE` → `DECLINED`, `declineReason=CARD_INACTIVE` (§2, шаг 2) |
| AUTH-03 | Статус `BLOCKED` → `DECLINED`, `declineReason=CARD_BLOCKED` (§2, шаг 2) |
| AUTH-04 | Статус `EXPIRED` → `DECLINED`, `responseCode=54` (§2, шаг 2) |
| AUTH-05 | `expiryDate` (MMYY) раньше текущей даты → `DECLINED`, `54` (§2, шаг 3) |
| AUTH-06 | Израсходовано за день + сумма ≤ `dailyLimit`, иначе `DECLINED`, `61` (§2, шаг 4; §4) |
| AUTH-07 | Израсходовано за месяц + сумма ≤ `monthlyLimit`, иначе `DECLINED`, `61` (§2, шаг 5; §4) |
| AUTH-08 | Сумма ≤ `availableBalance`, иначе `DECLINED`, `51` (§2, шаг 6) |
| AUTH-09 | Все проверки пройдены → `APPROVED`, `00`; сумма резервируется в CMS; RRN - 12 цифр, уникален; authCode - 6 символов `A-Z0-9` (§2, шаг 7; §3; §6) |

| AUTH-11 | Bin Lookup недоступен → берётся `issuerId` из таблицы BIN Switch, транзакция обрабатывается (§2, вариант B) |
| AUTH-12 | Проверки выполняются строго в порядке шагов 1-7; причину отказа определяет первая сработавшая проверка (§2) |
| AUTH-13 | Счётчики `limit_usage` растут только при одобренной авторизации (§4) |
| CMS-01 | `POST /api/cards`: PAN = BIN + 9 цифр + контрольная цифра Луна; `status=ACTIVE`; `expiryDate` = текущая дата + 3 года (MMYY) (§2) |
| CMS-02 | `GET /api/cards/{pan}` возвращает карту; если не найдена - 404 (§2) |
| CMS-03 | `GET /api/cards`: пагинация `limit` (50) / `offset` (0), фильтры `status`, `bin`; ответ `{total, cards}` (§2) |
| CMS-04 | `PATCH /api/cards/{pan}` меняет только переданные поля; допустимые статусы - `ACTIVE`, `INACTIVE`, `BLOCKED` (§2, `CardUpdateRequest`) |

| CMS-06 | `POST /api/cards/generate`: `count` 1-10000, `bins` ≥ 1; равномерно по BIN; баланс 10 000-500 000 ₽, дневной лимит 50 000-300 000 ₽, месячный = дневной × 30; статусы 95 / 3 / 2 % (§3, `GenerateCardsRequest`) |
| CMS-07 | PAN проходит проверку по алгоритму Луна (§4) |

| CMS-09 | Форматы полей карты: `bin` - 6 цифр, `currencyCode` - 3 цифры, `cardholderName` ≤ 255 символов, `expiryDate` - 4 цифры MMYY (§6, схема `Card`) |
| GW-01 | Смежное требование периферии: Gateway отклоняет `amount ≤ 0` и `pan` не из 16 цифр ответом 400 `VALIDATION_ERROR` (tz/02 §2) |

### Соглашения для тест-кейсов

- **К0** - новая карта из `POST /api/cards`: `bin=400000`, `cardholderName=IVAN IVANOV`, `currencyCode=643`, `dailyLimit=15000000`, `monthlyLimit=300000000`, `initialBalance=100000000` (все суммы в копейках).
- **T0** - `POST /api/transactions` по карте К0 с `amount=100000`, `terminalType=POS`, `mcc=5411`; остальные обязательные поля валидны (`mti=0100`, уникальный `stan`, `processingCode=000000`, `currencyCode=643`, текущее `transmissionDateTime`, `terminalId`, `merchantId`, `acquirerId`). В тест-кейсах указаны только отличающиеся поля.
- **d / m / b** - `dailyLimit` / `monthlyLimit` / `availableBalance`, задаются через `PATCH /api/cards/{pan}`.
- **SQL** - статус `EXPIRED` и `expiryDate` задаются прямо в таблице `cards`: через API их выставить нельзя.

## 3. Попарное тестирование (pairwise)

Для ядра построены две модели PICT - по одной на сервис:

| Сервис | Объект | Модель | Набор | Параметры / ограничения | Полный перебор → строк |
|---|---|---|---|---|---|
| Authorization | `POST /api/transactions` → решение по транзакции | [`pict/model.txt`](pict/model.txt) | [`pict/cases.txt`](pict/cases.txt) | 6 / 6 | 648 → 17 |
| Card-Management | `POST /api/cards` - создание карты | [`pict/card-management/model.txt`](pict/card-management/model.txt) | [`pict/card-management/cases.txt`](pict/card-management/cases.txt) | 6 / 1 + невалидные значения `~` | 1296 → 22 |

### Модель 1 - Authorization

| Параметр | Значения | Требования | Как задаётся |
|---|---|---|---|
| `card_status` | `ACTIVE`, `INACTIVE`, `BLOCKED`, `EXPIRED` | AUTH-02…04 | `PATCH status`; `EXPIRED` - SQL |
| `expiry` | `future`, `current_month`, `past` | AUTH-05 | К0 / SQL: текущий MMYY / SQL: предыдущий месяц |
| `amount_vs_daily` | `below`, `equal`, `above` | AUTH-06 | d = 150 000 / 100 000 / 99 999 |
| `amount_vs_monthly` | `below`, `equal`, `above` | AUTH-07 | m = 150 000 / 100 000 / 99 999 |
| `amount_vs_balance` | `below`, `equal`, `above` | AUTH-08 | b = 150 000 / 100 000 / 99 999 |
| `time_of_day` | `day`, `night` | сценарий `night_time` (tz/06 §3) | `transmissionDateTime` 14:00Z / 02:00Z текущего дня |

Сумма во всех строках - `amount = 100 000`; значения d, m, b выбраны так, что `below` - внутри класса, `equal` - точка ON, `above` - точка OFF (+1 копейка).

Ограничения модели 1:

| № | Ограничение | Основание |
|---|---|---|
| C1 | `EXPIRED` ⇒ `expiry = past` | Статус `EXPIRED` означает истёкший срок - другое сочетание противоречиво |
| C2 | `INACTIVE`/`BLOCKED` ⇒ `expiry ≠ past` | Иначе в строке два невалидных фактора, причину отказа не локализовать |
| C3 | Статус не `ACTIVE` ⇒ лимиты и баланс `below` | Отказ на шаге 2 (AUTH-12): лимиты и баланс не проверяются, их невалидные значения только маскировали бы причину |
| C4 | `expiry = past` ⇒ лимиты и баланс `below` | Отказ на шаге 3 |
| C5 | `amount_vs_daily = above` ⇒ месячный лимит и баланс `below` | Отказ на шаге 4 - один невалидный фактор |
| C6 | `amount_vs_monthly = above` ⇒ баланс `below` | Отказ на шаге 5 - один невалидный фактор |

Обоснование и расчёт для модели 1:

- **Зачем.** Решение по транзакции зависит от пяти параметров карты. Шестой параметр - время транзакции (`time_of_day`): по ТЗ на решение оно влиять не должно, но ночные лимиты описаны как «если реализованы», то есть связь времени с лимитами не формализована. Pairwise покрывает все пары параметров карты без полного перебора и проверяет, что решение не меняется от сочетания времени с состоянием карты.
- **Расчёт.** Полный перебор - 4 × 3 × 3 × 3 × 3 × 2 = **648** комбинаций, ограничениям удовлетворяют 72. Допустимых пар значений - **100**. Нижняя граница - не меньше 8 строк: столько допустимых пар у `card_status` × `expiry` и у `card_status` × `time_of_day`. PICT выдал **17** строк - сокращение в 38 раз от полного перебора. Строк больше нижней границы, потому что ограничения C3-C6 разрешают значения `equal`/`above` только при `ACTIVE`, и эти пары нельзя разложить по строкам с другими статусами.
- **Проверка.** Отдельный скрипт перебрал все 648 комбинаций, отфильтровал их по C1-C6 и подтвердил: покрыто 100 из 100 допустимых пар, ни одна строка набора не нарушает ограничения.

Ограничения модели 2:

| № | Ограничение | Основание |
|---|---|---|
| `~` | В строке не больше одного невалидного значения (встроенная семантика PICT для значений с `~`) | Правило «один невалидный класс - один тест-кейс»: причина отказа в каждой негативной строке однозначна |
| C1 | `daily_limit = negative` ⇒ `monthly_limit = above_daily` | `equal_daily` при отрицательном дневном лимите тоже даёт отрицательный месячный - это второй невалидный фактор |

Обоснование и расчёт для модели 2:

- **Зачем.** Создание карты - шесть независимых полей, у каждого свои валидные и невалидные классы. Валидные границы (`len_255`, `min_1`, `zero`, `equal_daily`) могут взаимодействовать при сохранении в БД: например, имя длиной 255 символов вместе с нулевым балансом. Pairwise проверяет каждую пару валидных значений и каждое невалидное значение на фоне разных валидных.
- **Расчёт.** Полный перебор - 4 × 4 × 3 × 3 × 3 × 3 = **1296** комбинаций, с учётом правила `~` и C1 допустимо 304. Пар валидных значений - **60** (статистика PICT `/s`), всего пар вместе с невалидными - **139**. PICT выдал **22** строки: 6 позитивных и 16 негативных; сокращение в 59 раз.
- **Проверка.** Скрипт подтвердил: покрыто 139 из 139 пар, в каждой строке не больше одного невалидного значения, C1 не нарушено.

### Критичные сочетания вне попарного покрытия

2-wise не гарантирует взаимодействие трёх и более факторов. Критичные тройки проверены на наличие в сгенерированных наборах, недостающие добавлены вручную отдельными тест-кейсами:

| Сочетание | Почему критично | Где покрыто |
|---|---|---|
| Все три границы ON одновременно: d = m = b = сумма | Off-by-one (`<` вместо `≤`) в любой из трёх проверок даёт ложный отказ; при одобрении баланс становится ровно 0 | В набор не попало - добавлено вручную: TC-AUTH-12 |
| Оба лимита ON, баланс OFF | Прохождение лимитов «впритык» не должно прерывать цепочку: шаг 6 (баланс) обязан выполниться | Модель 1, строка 03 → TC-PW-AUTH-03 |
| Накопленный расход + сумма = остаток лимита | Зависит от истории транзакций - одной строкой набора не выражается | Вручную: TC-AUTH-04, TC-AUTH-08, TC-AUTH-15, TC-AUTH-16 |
