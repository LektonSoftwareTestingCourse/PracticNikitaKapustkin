# Тестовый план СМП

## 1. Область и подход

**Область.** Вся система СМП. Глубина зависит от слоя:

| Слой | Сервисы | Что проверяется |
|---|---|---|
| Ядро | Authorization, Card-Management | Шаги 1-7 авторизации, коды `00/05/14/51/54/61`, резервирование, `limit_usage`, CRUD и генератор карт, Луна, `expiryDate` |
| Периферия | Gateway, Switch, Transaction Logger, Terminal/Merchant Simulator, Web Dashboard, Bin Lookup, Notification Service | Валидация и rate limit, маршрутизация BIN → issuer, откат с кодом `96`, журнал и поиск, сценарии симуляторов, отображение |

**Подход.** Чёрный ящик по требованиям, риск-ориентированный приоритет (P1 → P2 → P3). Техники: классы эквивалентности, граничные значения (тройки точек), попарное тестирование. Порядок выполнения: дымовой чек-лист → позитивные тест-кейсы ядра → негативные тест-кейсы ядра → pairwise-набор → критический путь периферии.

## 2. Критерии входа и выхода

**Критерии входа**:

- стенд поднят командой `docker compose up -d`, все 11 сервисов, PostgreSQL и RabbitMQ в статусе `healthy`;
- `scripts/smoke-test.sh` завершился с `ALL CHECKS PASSED`, дымовой чек-лист пройден полностью;
- тестовые карты сгенерированы через `POST /api/cards/generate` по всем BIN `400000`-`400004`: без пула карт не работают Terminal Simulator и проверки периферии;
- версии ТЗ и `openapi.yaml` зафиксированы коммитом;
- модели PICT прошли ревью, `pict/cases.txt` и `pict/card-management/cases.txt` сгенерированы из текущих версий моделей;
- есть доступ к БД стенда для подготовки данных (`EXPIRED`, `expiryDate`).

**Критерии выхода**:

- выполнено 100 % тест-кейсов ядра (`TC-AUTH-*`, `TC-CMS-*`, `TC-PW-*`);
- нет открытых дефектов уровней Critical и High;
- у каждого требования ядра (`AUTH-01`…`AUTH-13`, `CMS-01`…`CMS-09`) есть хотя бы один выполненный тест-кейс;
- все коды ответа `00`, `05`, `14`, `51`, `54`, `61` получены хотя бы одним тест-кейсом;
- все пары значений обеих моделей PICT покрыты выполненными строками наборов.

**Критерии приостановки:**

- упал хотя бы один пункт дымового чек-листа или сервис ядра перешёл в `unhealthy`;
- не проходит позитивный тест-кейс одобрения (`TC-AUTH-01`): негативные результаты без него неинформативны;
- найден дефект уровня Critical, блокирующий цепочку Gateway → Switch → Authorization;
- изменилось ТЗ ядра или API-контракт - тест-кейсы нужно пересмотреть.

**Критерии возобновления:** исправление развёрнуто на стенде, дымовой чек-лист снова пройден, первым повторно выполняется `TC-AUTH-01`, затем тест-кейсы, затронутые исправлением или изменением ТЗ.

## 3. Ресурсы и расписание

**Ресурсы:**

| Ресурс | Состав |
|---|---|
| Люди | 1 тестировщик - дизайн, выполнение, отчётность; куратор курса - ревью и ответы на вопросы по ТЗ |
| Окружение | Локальный стенд Docker Compose (macOS, Docker Desktop): 11 сервисов + PostgreSQL 16 + RabbitMQ 3.13 |
| Инструменты | Java 21 + Maven. JUnit 5 + Mockito, REST Assured, Testcontainers. Тест-дизайн: PICT. Ручные проверки: curl / REST-клиент, PostgreSQL для подготовки данных. CI: GitHub Actions |

**Расписание**:

| Этап | Содержание | Срок |
|---|---|---|
| Практика 1 | Стенд и smoke - критерии входа | неделя 3 (выполнено) |
| Практика 2 | Стратегия, план, test-design ядра, PICT, чек-листы | неделя 5 |
| Практика 3 | Unit-тесты ядра по классам и границам из test-design | неделя 7 |
| Практика 4 | API/интеграционные тесты: все эндпоинты и decline-коды | неделя 9 |
| Практика 5 | E2E-сценарии и баг-репорты | неделя 11 |
| Практика 6 | CI/CD и нагрузочный smoke, Test Summary Report | неделя 13 |
| Практика 7 | Метрики и отчётность | неделя 15 |
| Практика 8 | Финальная тестовая стратегия, защита | неделя 16 |

## 4. Риски

| № | Риск | Вероятность / влияние | Меры по снижению риска |
|---|---|---|---|
| R1 | Тестовый стенд недоступен или работает нестабильно | Средняя / высокое | Дымовой чек-лист перед каждым прогоном |
| R2 | Требования неполные или меняются в ходе тестирования | Высокая / высокое | Вопросы аналитику до начала работ; при изменении требований - пересмотр затронутых тест-кейсов |
| R3 | Не хватает времени на выполнение всех проверок | Средняя / высокое | Проверки выполняются по приоритету P1 → P2 → P3 |
| R4 | Дефекты исправляются с задержкой и блокируют тестирование | Средняя / среднее | Пока дефект не исправлен, выполняются незаблокированные проверки |

## 5. Метрики

| Метрика | Условие | Цель |
|---|---|---|
| Выполнение | Доля тест-кейсов, которые запущены, с любым результатом | 100 % |
| Прохождение | Доля запущенных тест-кейсов, у которых фактический результат совпал с ожидаемым | ≥ 95 % |
| Покрытие требований | Доля требований ядра, которые проверены хотя бы одним запущенным тест-кейсом | 100 % |
| Покрытие кодов ответа | Доля кодов `00`, `05`, `14`, `51`, `54`, `61`, которые система вернула хотя бы в одном тест-кейсе | 100 % |
| Попарное покрытие | Доля пар значений из моделей PICT, которые встретились хотя бы в одном запущенном тест-кейсе | 100 % |
| Дефекты | Сколько найденных дефектов ещё не исправлено, по уровням Critical / High / Medium / Low | Critical и High = 0 |
