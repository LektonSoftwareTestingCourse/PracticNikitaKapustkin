# Тестовая стратегия СМП

**Объект тестирования** - СМП, симулятор процессингового центра: микросервисная система, которая проводит карточную транзакцию от POS-терминала до решения эмитента и обратно.

## 1. Цель тестирования

**Цель** - подтвердить, что СМП принимает корректное и воспроизводимое решение по каждой карточной транзакции: `APPROVED` с кодом `00` либо `DECLINED` с правильным `responseCode` и `declineReason` (`05`, `14`, `51`, `54`, `61`, `96`). Решение должно соответствовать статусу, сроку действия, лимитам и балансу карты, а его последствия - одинаково отражаться во всех подсистемах: резерв в Card-Management, счётчики `limit_usage` в Authorization, запись в Transaction Logger (через RabbitMQ), статистика на Web Dashboard и события в Notification Service.

## 2. Уровни проверок

- **Модульный** - бизнес-правила сервисов (шаги авторизации, алгоритм Луна, RRN) проверяются быстро и без стенда.
- **Интеграционный / API** - большинство отказов возникает на стыках сервисов: CMS и Authorization, Switch и Logger.
- **Системный (E2E)** - только сквозная цепочка показывает, согласованы ли данные при асинхронной доставке через RabbitMQ.
- **Дымовой** - быстрый фильтр перед любым прогоном: без рабочего стенда остальные результаты неинформативны.

## 3. Область тестирования и обоснование исключений

**Входит в область.** Функциональность, которая определяет решение по транзакции и движение денег:

- **ядро** - Authorization (проверка статуса, срока действия, лимитов и баланса карты, резервирование, `limit_usage`, `ISSUER_TIMEOUT`, fallback при недоступности Bin Lookup) и Card-Management (CRUD, генератор, алгоритм Луна, статусы, `expiryDate` MMYY, `reserve`);
- **периферия** - Gateway (валидация, проксирование, rate limit, 503), Switch (маршрутизация BIN → issuer, reversal с кодом `96` при сбое Logger), Transaction Logger (приём из очереди, идемпотентность, поиск, статистика, WebSocket), Terminal/Merchant Simulator (сценарии нагрузки), Web Dashboard (отображение), Bin Lookup и Notification Service (асинхронные события карт).

**Вне области:**

| Исключение | Основание |
|---|---|
| Тестирование безопасности (PCI DSS, шифрование каналов, аутентификация) | Замкнутый учебный контур: данные синтетические, реальных PAN и внешних сетей нет - вероятность и ущерб утечки близки к нулю |
| Бинарный протокол ISO 8583 и реальные платёжные системы | В СМП ISO 8583 эмулируется JSON, внешних BIN нет - проверять нечего, риск не существует |
| Кроссбраузерность и визуальная вёрстка Dashboard | Dashboard только отображает данные Logger и не влияет на решение по транзакции; проверяется корректность данных, а не пиксели |
| Бонусные функции (PIN/CVV/3-D Secure stubs, ночные лимиты, кэш карт) | Не обязательны по ТЗ; включаются в область, только если реализованы, иначе ожидаемое поведение не определено |
| Отказоустойчивость самих PostgreSQL и RabbitMQ | Это стороннее ПО; проверяется только реакция СМП на их недоступность (503, откат, retry), а не сами продукты |

## 4. Подход и принципы приоритизации

**Подход - риск-ориентированный**, дополненный аналитическим (проверки выводятся из разбора ТЗ и API-контракта) и чек-листным (для периферийных сервисов). Приоритет проверки = вероятность дефекта × ущерб от него.

| Приоритет | Область | Риск |
|---|---|---|
| P1 - критический | Решение Authorization, лимиты, баланс, резервирование в CMS, статусы и срок действия карты | Прямой финансовый ущерб: списание сверх лимита или баланса, отказ по валидной карте |
| P2 - высокий | Маршрутизация Switch, откат при сбое Logger, уникальность RRN, идемпотентность Logger, валидация и rate limit Gateway | Потеря или дублирование транзакций, рассинхронизация резерва и журнала |
| P3 - средний | Симуляторы, статистика и WebSocket Dashboard, Notification Service | Искажается картина для оператора, деньги не страдают |

Принципы:

1. **Сначала то, через что проходит каждая транзакция.** Gateway, Switch, Authorization и Card-Management участвуют в любой покупке: дефект в них останавливает весь платёжный поток. Сбой Dashboard или симулятора на проведение платежей не влияет.
2. **Сначала позитивный сценарий, затем негативные.** Отказ по невалидным данным что-то доказывает, только если одобрение валидной транзакции уже работает.
3. **В тест-кейсе не больше одного невалидного значения.** Иначе нельзя понять, какая проверка вызвала отказ.
4. **Ложное одобрение опаснее ложного отказа.** Одобрение сверх лимита или баланса - прямой убыток, отказ по валидной карте - недовольный клиент. Поэтому проверки статуса, лимитов и баланса карты идут первыми.
5. **Деньги и журнал всегда сходятся.** Одобренная транзакция резервирует сумму ровно один раз и ровно один раз попадает в журнал. При сбое Logger или брокера резерв откатывается.
