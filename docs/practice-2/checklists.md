# Чек-листы

## 1. Дымовое тестирование

Выполняется после каждой сборки и перед любым прогоном. Любой непройденный пункт - критерий приостановки тестирования.

### 1.1 Инфраструктура

- [ ] Все контейнеры стенда запущены и находятся в статусе `healthy`: 11 сервисов, PostgreSQL, RabbitMQ
- [ ] Порты сервисов на хосте свободны и опубликованы в соответствии с `.env`
- [ ] PostgreSQL принимает подключения, таблицы сервисов созданы миграциями
- [ ] RabbitMQ Management UI открывается под учётной записью из `.env`
- [ ] Очереди `transaction-log` и `card-notifications` существуют, у каждой есть потребитель
- [ ] В логах сервисов после старта нет записей уровня `ERROR`

### 1.2 Доступность сервисов

- [ ] Health-check Gateway отвечает `ok` и сообщает о состоянии downstream-сервисов
- [ ] Health-check `/health` отвечает у Card-Management, Switch, Authorization, Terminal Simulator, Merchant Simulator, Transaction Logger
- [ ] Health-check `/actuator/health` отвечает у Bin Lookup и Notification Service

### 1.3 Карты

- [ ] Генерация тестовых карт через Gateway создаёт карты по всем BIN
- [ ] Создание одной карты возвращает карту в статусе `ACTIVE`
- [ ] Список карт возвращается и не пуст
- [ ] Карта находится по PAN
- [ ] Bin Lookup возвращает эмитента по BIN

### 1.4 Транзакции

- [ ] Транзакция по активной карте проходит через Gateway и одобряется
- [ ] Баланс карты после одобрения уменьшился на сумму транзакции
- [ ] Транзакция по заблокированной карте отклоняется

### 1.5 Журнал, дашборд и уведомления

- [ ] Одобренная транзакция находится в журнале поиском по PAN
- [ ] Статистика дашборда учитывает новую транзакцию
- [ ] Список последних транзакций содержит новую транзакцию
- [ ] Web Dashboard открывается и отображает KPI-карточки
- [ ] Notification Service возвращает список уведомлений

### 1.6 Симуляторы

- [ ] Terminal Simulator выполняет короткий прогон сценария `normal` без ошибок
- [ ] Merchant Simulator выполняет короткий прогон одного сценария без ошибок
- [ ] Список мерчантов возвращается и не пуст

## 2. Критический путь

Ключевые сценарии процессинговой цепочки. Для периферийных сервисов пункты сформулированы как классы верхнего уровня: каждый класс проверяется отдельно, по одному невалидному фактору за проверку.

### 2.1 Покупка: сквозная цепочка (P1)

- [ ] Транзакция проходит всю цепочку: Terminal Simulator → Gateway → Switch → Authorization → Card-Management → RabbitMQ → Transaction Logger
- [ ] Одобрение резервирует сумму: баланс карты уменьшается ровно на сумму транзакции
- [ ] Одобренная транзакция увеличивает израсходованный дневной и месячный лимит карты
- [ ] RRN одинаков в ответе клиенту, в журнале Logger и на Dashboard
- [ ] Запись попадает в журнал после доставки через очередь, ровно один раз
- [ ] Новая транзакция появляется на Dashboard в реальном времени (WebSocket), без перезагрузки страницы

### 2.2 Отказы проходят по цепочке без искажений (P1)

- [ ] Отклонённая транзакция не меняет баланс карты и израсходованные лимиты
- [ ] Каждая причина отказа (`14`, `51`, `54`, `61`, `CARD_INACTIVE`, `CARD_BLOCKED`, `ISSUER_TIMEOUT`) доходит до клиента и журнала неизменной
- [ ] Отказы учитываются в `declinedCount` и `approvalRate` статистики

### 2.3 Gateway (P2)

- [ ] Запрос со всеми обязательными полями принимается; отсутствие любого обязательного поля отклоняется с `VALIDATION_ERROR` - по одному полю на проверку
- [ ] Форматы полей: `pan` - 16 цифр, `amount` > 0, `currencyCode` - 3 символа, `mcc` - 4 цифры, `stan` не пустой, `mti` = `0100`
- [ ] Rate limit `/api/transactions`: частота ниже 100 запросов/с, ровно на пороге и выше порога - выше порога ответ 429 с `retryAfterMs`
- [ ] Каждый префикс пути (`/api/cards/**`, `/api/transactions`, `/api/transactions/search`, `/api/simulator/**`, `/api/dashboard/**`) проксируется в свой сервис
- [ ] Недоступность downstream-сервиса → 503 `SERVICE_UNAVAILABLE` с именем сервиса

### 2.4 Switch (P2)

- [ ] Каждый BIN из таблицы (`400000`-`400004`) маршрутизируется к своему эмитенту (`ISS001`-`ISS005`)
- [ ] BIN вне таблицы отклоняется с кодом `14`
- [ ] Если брокер не подтвердил публикацию одобренной транзакции, выполняется откат резерва (reversal `0400`), клиент получает `96`, баланс восстановлен

### 2.5 Transaction Logger (P2)

- [ ] Повторный приём транзакции с тем же `id` не создаёт дубликат
- [ ] Поиск: каждый фильтр (`pan`, `status`, период, `merchantId`, `issuerId`, `mcc`) по отдельности и в комбинации (логика AND); без фильтров - все записи
- [ ] Пагинация поиска `limit` / `offset` и значения по умолчанию
- [ ] Статистика согласована: `totalTransactions` = `approvedCount` + `declinedCount`, `approvalRate` = `approvedCount` / `totalTransactions`
- [ ] Экспорт транзакций возвращает те же записи, что и поиск с теми же фильтрами

### 2.6 Симуляторы (P3)

- [ ] Запускается каждый сценарий Terminal Simulator: `normal`, `mixed`, `high_value`, `night_time`, `declines_test`
- [ ] Доля отказов в прогоне соответствует описанию сценария (`normal` - без отказов, `declines_test` - около 80 % отказов)
- [ ] Непрерывный режим: запуск, статус, остановка
- [ ] Запускается каждый сценарий Merchant Simulator (`grocery`, `electronics`, `restaurant`, `travel`), MCC соответствуют сценарию
- [ ] Комиссия эквайера рассчитывается по ставке MCC

### 2.7 События карт и устойчивость (P3)

- [ ] Создание, изменение и удаление карты публикуют событие, Notification Service его получает
- [ ] При временной недоступности RabbitMQ событие карты доставляется после восстановления брокера
- [ ] При недоступности Bin Lookup авторизация продолжает работать (штатная деградация)
- [ ] После перезапуска Logger Dashboard восстанавливает WebSocket-соединение и данные
